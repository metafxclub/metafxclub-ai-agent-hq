# ซิงก์ Google Sheets เป็นชุดย่อย

งานชีตย้ายออกจาก Dashboard scheduler ที่เป็นเงื่อนไข Health ของ HQ แล้ว ใช้ Sheet service เพียงชุดเดียว โดย Bridge เป็นผู้เขียน outbox/cache/settings เดิม ส่วนการติดต่อ Google และแปลงรายงานทำใน Sheet executor คนละ process งานสภา AI, EA และกติกาเปิดออเดอร์ไม่เปลี่ยน

## การแยกเมื่อเกิดปัญหา

- งานอัตโนมัติและการกดซิงก์/ตรวจ/อ่านชีตเองใช้ executor เดียวกัน ไม่มีการย้อนกลับไปติดต่อ Google ใน Bridge เมื่อ executor ใช้ไม่ได้
- การบันทึกรายงานเก็บ intent ของแต่ละรายงานไว้ในเครื่องแล้วคืนผลทันที ไม่ต้องรอ Google และไม่จำกัดการกู้คิวไว้เพียงหน้าต่าง 240 รายงาน
- Worker รับงานผ่าน pipe ภายในเครื่อง ไม่เก็บ job payload หรือ credentials ลง log ไม่แก้ไฟล์ outbox/settings/audit และไม่เปิด Council/MT5/Agent เพิ่ม
- ก่อนส่งแถว บันทึกสถานะยังยืนยันผลไม่ได้ไว้ถาวร ถ้า worker หรือ Bridge หยุดกลางทางจะตรวจด้วย key เดิมก่อนยืนยันผล ไม่ถือว่ารับงานแล้วแปลว่าส่งสำเร็จ
- จำกัดเวลารอ worker และหยุดเฉพาะ child ที่สร้างเองเมื่อหมดเวลา ไม่มีการสั่งหยุด HQ หรือ MT5 จากความผิดพลาดของชีต
- มี lease กัน worker ซ้ำใน project เดียวกัน และ child ตรวจอายุ parent เพื่อไม่เหลือ process ส่งชีตค้างหลัง Bridge จบ
- `researchSheetService` ใน Health แสดงสถานะและ error แยกจากสภา AI โดยไม่ใช้ตัดสิน core readiness ส่วนเกณฑ์ตรวจ Council/mission worker/dashboard scheduler เดิมยังอยู่ครบ

Bridge ยังมี coordinator สำหรับเก็บคิวและรับผลกลับ การแยกนี้ป้องกันการค้าง/ล้มของงาน Google และการแปลงรายงานลากบริการเทรดล้มตาม แต่ยังใช้ CPU, RAM, disk และระบบปฏิบัติการเครื่องเดียวกัน

## การทำงาน

- ในหนึ่ง tick ของ Sheet service ทำงานชีตเพียงหนึ่งขั้นตอน โดยเลือกงานที่ถึงกำหนดก่อน เพื่อให้ทุกขั้นตอนได้ทำงาน Dashboard scheduler ไม่เรียกขั้นตอนเหล่านี้แล้ว
- ตรวจรายงานย้อนหลังไม่เกิน 2 รายงานที่เข้าเกณฑ์ต่อชุด และตรวจเวลาที่ใช้ระหว่างงาน โดยตั้ง budget ไว้ 8 วินาที
- เก็บตำแหน่งสแกนไว้ทำต่อใน tick ถัดไป ใช้ขอบเขตรายงานล่าสุด 240 รายการตามเดิม และเรียงเก่าไปใหม่ รายงานที่แก้ไขระหว่างสแกนจะกลับมาตรวจท้ายคิว
- เมื่อเปลี่ยนชีตหรือ config revision จะเริ่มสแกนใหม่ เมื่อ restart จะสร้างตำแหน่งสแกนใหม่จากรายงานที่เก็บไว้ การส่งซ้ำถูกป้องกันด้วย payload digest และใบรับผลใน outbox เดิม
- ส่งหนึ่งแถวต่อรอบส่งข้อมูล คิวว่างจะไม่อ่านสถานะ credentials งาน OAuth/Sheets ในรอบเบื้องหลังใช้ budget เครือข่ายร่วม 40 วินาทีและจำกัด timeout ของแต่ละ request ตามเวลาคงเหลือ
- กู้ deferred report ครั้งละหนึ่งรายการ และอ่านข้อมูลกลับเข้า cache ครั้งละหนึ่งกลุ่ม แยกจากขั้นตอนส่งแถวข้อมูล
- การ refresh cache บางกลุ่มไม่ทำให้ข้อมูลเก่าของกลุ่มอื่นดูสดขึ้น และไม่เขียนทับ cache ของชีต/revision ที่ถูกเปลี่ยนระหว่างทาง

Budget เป็นการตรวจระหว่างขั้นตอน ไม่ใช่การบังคับตัด thread: การตรวจรายงานหนึ่งรายการที่เริ่มแล้ว, OS/file lock หรือการอ่าน response ที่อยู่ระหว่างทำงานอาจใช้เวลาเกิน budget ได้ จึงต้องตรวจระยะเวลาจริงบนเครื่องด้วย เกณฑ์ Health 120 วินาทีและ heartbeat ไม่ได้ถูกผ่อนให้แสดงผ่าน

## การรักษาข้อมูล

- คงการตรวจสิทธิ์ ชื่อคอลัมน์ key ของแถว หลักฐานรายงาน และการยืนยันผลอ่านกลับ
- เมื่อหมดเวลาหรือขัดข้องก่อนเขียน จะเก็บงานไว้รอ retry ตาม backoff
- เมื่อพยายามเขียนแล้วแต่ยืนยันผลไม่ได้ ใช้ `write_unknown` แล้วตรวจด้วย key เดิม ห้ามสรุปว่าส่งสำเร็จหรือเพิ่มแถวใหม่โดยไม่ตรวจ
- รายงานเสียไม่ขวางรายงานถัดไป ส่วนการเขียน local store ที่ผิดพลาดจะคง cursor ให้ลองรายการเดิมได้
- การสั่งซิงก์/ตรวจชีตแบบ manual ยังคงขั้นตอนเดิม รวมถึง full backfill และการ refresh cache ครบกลุ่ม แต่ Google I/O ทั้งหมดผ่าน executor ที่มีเวลารอจำกัด

## การตรวจสอบ

ใช้ `test_sheet_process_isolation.py`, `test_research_sheet_background_batches.py` และ `test_scheduler_phase_observability.py` ร่วมกับ regression ของ Research Sheet, Google OAuth, scheduler และ Council โดยใช้ข้อมูลจำลอง/โฟลเดอร์ชั่วคราวและบล็อกการเชื่อมต่อภายนอก ตรวจ worker ค้าง/ตาย/ตอบผิด, การกู้ intent เกิน 240 รายงาน, ผลเขียนที่ไม่แน่ชัด และยืนยันว่าสถานะชีตไม่กลบหรือทำลาย core Health

การติดตั้งในเครื่องที่มี MT5 ทำงานอยู่ต้องตรวจว่าไม่มี Council/Agent job หรือคำสั่งเทรดค้างก่อนหยุดเฉพาะ Bridge แบบ graceful เก็บไฟล์ย้อนกลับ และเปรียบเทียบสถานะบัญชี/จำนวน position/EA heartbeat/config ก่อนและหลัง โดยไม่ restart terminal หรือส่งออเดอร์ทดสอบ
