# สภา AI: เริ่มพร้อมกันและใช้งบเวลารอบเดียว

เอกสารนี้อธิบายแพตช์คิวสภา AI สำหรับรอบอัตโนมัติที่ตรวจพบแท่งใหม่ ไม่เปลี่ยนตรรกะส่งคำสั่งของ EA MT4/MT5 และไม่เปิด Live หรือปรับออเดอร์ที่มีอยู่

## พฤติกรรมของรอบอัตโนมัติ

1. เมื่อระบบตรวจพบแท่งปิดใหม่และผ่านโควตา จะตรึงเวลารับรอบนั้นไว้ที่ `quotaAdmittedAt` และกำหนด `triggerExpiresAt` ไม่เกิน **300 วินาที** หลังเวลานั้น
2. เวลาที่เตรียม Snapshot, คำนวณข้อมูล, ประกอบ Prompt, บันทึก Mission, รอ Worker และเรียก Runner ใช้งบก้อนเดียวกัน ไม่เริ่มนับ 300 วินาทีใหม่หลังสร้างคิวเสร็จหรือหลัง Agent รับงาน
3. Manager parent และงานของ Technical, Price Action, News ใช้ `roundStartedAt` และ `roundDeadlineAt` ชุดเดียวกัน รวมถึง Snapshot artifact และ digest เดียวกัน
4. Worker สภา AI สามตัวรับคนละบทบาท แล้วเริ่มทำงานพร้อมกันได้ ไม่ต้องรอ Technical ตอบก่อนจึงเริ่ม Price Action หรือ News
5. เมื่อหมดเวลา เปลี่ยนแท่ง เปลี่ยน stream หรือรอบไม่ครบเงื่อนไข จะไม่ใช้ผลเก่าเพื่อส่งคำสั่งใหม่ ไม่มีการสะสมรอบที่พลาดเพื่อวิเคราะห์ย้อนหลังเมื่อโควตากลับมา

**300 วินาทีเป็นเพดานรวม ไม่ใช่การรับประกันว่าจะรันครบ 300 วินาที** แต่ละบทบาทยังมี timeout ของตนเอง ความสดของ Snapshot/ราคา และ Guard ของ EA อาจทำให้รอบสิ้นสุดหรือถูกบล็อกก่อน เพดานโควตาและข้อจำกัดจากผู้ให้บริการยังคงใช้ตามเดิม

เพดานนี้สิ้นสุดที่การตัดสินใจและรับคำสั่งเข้า Gateway ไม่ใช่เวลาที่ Broker ยืนยันเปิดออเดอร์สำเร็จ คำสั่งที่เผยแพร่ไปแล้วใช้ TTL, ACK และขั้นตอนตรวจผลเดิม แพตช์นี้ไม่แก้คำสั่งที่อยู่ระหว่างทาง

## แยกเวลาเตรียมงานออกจากเวลารัน AI

| บทบาท | เวลา Runner | ต้องเตรียมพร้อมก่อนวินาทีที่นับจากรับรอบ |
| --- | ---: | ---: |
| Technical | 60 วินาที | 205 |
| Price Action | 60 วินาที | 205 |
| News | 90 วินาที | 175 |

เมื่อเตรียมพร้อมจึงเริ่มจับเวลาการรัน โดยเผื่อการส่งผลและหยุด Process อีก 30 วินาที และเหลืออย่างน้อย 5 วินาทีก่อนเส้นตายรวม ไม่ได้รวมเวลารันทั้งสามตัวต่อกันเป็นลำดับ หากเหลือเวลาไม่พอสำหรับบทบาทนั้น ระบบหยุดรอบไว้ตามเงื่อนไขเดิม

Heartbeat และการขอเริ่มซ้ำไม่เลื่อนเส้นตาย การเริ่ม Process มีหลักฐานบันทึกครั้งเดียวตาม lease; ถ้าบันทึกไม่สำเร็จจะหยุดเฉพาะ Process ที่เพิ่งสร้าง Watchdog บันทึกสถานะหมดเวลาแล้วปล่อย lock ก่อนหยุด Process เพื่อไม่ขวางงานตัวอื่น และไม่รับผลสำเร็จที่ย้อนกลับมาหลังถูกปิดรอบ

## ลดเวลาที่เสียกับประวัติ Mission

ประวัติ Mission ถูกเก็บไว้ครบเพื่อการตรวจย้อนหลัง การสร้าง parent และ child สามงานจึงใช้ working copy ของ Mission store ภายใต้ lock เดิม และบันทึกทั้งกลุ่มด้วยการแทนที่ไฟล์ `missions.json` เพียงครั้งเดียว

- ผู้อ่านอีก thread เห็น store เดิมที่สมบูรณ์ หรือกลุ่มใหม่ที่ประกอบครบ ไม่เห็น parent ที่มี child พร้อมรันเพียงหนึ่งหรือสองบทบาท
- การอนุญาต, idempotency, รายการตรวจสอบและ audit ของ `create_mission` ยังทำงาน
- ถ้าประกอบรอบล้มเหลว จะคงหลักฐาน parent/child ที่ล้มเหลวในสถานะ blocked ไม่เผยแพร่คิวบางส่วนที่ยังรันได้
- ไม่ลบประวัติเดิม ไม่คัดลอกข้อมูลจากเครื่องใช้งานจริงเข้าชุดทดสอบ และไม่สร้าง scheduler อีกชุดมาซ้อน

## ไม่ให้คำตอบที่ช้าเปิดออเดอร์ย้อนหลัง

Worker ตรวจสิทธิ์เริ่มงานทั้งก่อน claim และหลัง claim รวมถึงก่อนเรียก Runner โดยใช้ deadline เดิม ผลที่กลับมาช้าจะไม่ทำให้ deadline ยืดออก การตัดสินใจและจุดเผยแพร่คำสั่งของ Gateway ยังตรวจเวลาซ้ำ การมีผลวิเคราะห์บันทึกไว้จึงไม่เท่ากับมีคำสั่งซื้อขายถูกเผยแพร่

หลัง Bridge เริ่มใหม่ งานอัตโนมัติที่ผูกกับ startup เดิมไม่ถูกนำไปรันเป็นรอบย้อนหลัง เช่นเดียวกับงานจากแท่งก่อนหน้าเมื่อแท่งล่าสุดเปลี่ยนแล้ว รอบที่ role ใดล้มเหลวไม่เริ่ม role นั้นซ้ำบนแท่งเดิมโดยอัตโนมัติ

## ส่วนที่ยังเหมือนเดิม

- รอบที่ผู้ใช้สั่งเองยังใช้สัญญาเวลาเดิม **240 วินาที**; แพตช์นี้ไม่ได้เพิ่มเวลารอบ manual
- Admission เก่าที่บันทึก deadline สั้นกว่า เช่น 60 วินาที ไม่ถูกแปลงย้อนหลังให้มีเวลาเพิ่ม
- Symbol/Timeframe/Channel, บัญชี Demo/Live, ลายเซ็น, Magic, Lot, Risk Guard และ idempotency การส่งคำสั่ง MT4/MT5 ไม่ถูกลดเงื่อนไข
- ข้อมูลปัจจุบันจาก Broker ยังต้องตรงกับแท่งและ stream ที่รอบอ้างอิง การตีความเวลาของแท่ง Broker แยกจาก UTC deadline ของรอบ
- ไม่ทดสอบด้วยการส่งออเดอร์บนบัญชีจริง และไม่ restart Terminal ที่กำลังดูแลออเดอร์เพื่อทดสอบแพตช์นี้

## หลักฐานการทดสอบที่ทำซ้ำได้

`tests/test_council_parallel_round_budget.py` ใช้ queue builder, Mission store, selector, claim, worker และ finish path จริง แต่แทน Runner ด้วย stub ที่ไม่เรียก AI และเปลี่ยนเวลาใน clock จำลองโดยไม่รอ 300 วินาทีจริง

กรณีสำคัญ:

- มีประวัติจำลอง 1,200 รายการ และเพิ่มเวลาเตรียม Prompt ด้วย clock จำลอง: deadline ยังเท่ากับเวลารับรอบ + 300 วินาที
- ขอรอบเดิมซ้ำ: มี parent เดียวและ child สามบทบาทชุดเดิม
- Worker จริงสามตัวต้องเข้าถึง Runner ทั้งหมดก่อนปล่อยผลแรก และใช้ Snapshot/digest เดียวกัน
- บันทึก Mission archive หนึ่งครั้งต่อกลุ่ม และผู้อ่านอีก thread ไม่เห็นกลุ่มที่ประกอบค้าง
- ประกอบ child ตัวที่สองล้มเหลว: ไม่มีคิวบางส่วนที่รันได้ และประวัติเดิมยังอยู่
- บันทึก parent ขั้นสุดท้ายล้มเหลวหลังสร้าง child ครบ: ทั้งสี่งานถูกบล็อก และ shared read cache เดิมไม่ถูกแก้จาก working copy
- การแทนที่ Mission archive ขั้นสุดท้ายล้มเหลวหลังเขียน staging/backup: store และ cache เดิมยังสมบูรณ์ ไม่มีคิวใหม่หลุดออกมา และประกอบรอบใหม่ได้เมื่อข้อผิดพลาดหายไป
- หมดเวลาหลัง claim: ไม่เรียก Runner และไม่หักสิทธิ์เรียกงานแบบ consume
- คำตอบทั้งหมดช้า, role บางตัวล้มเหลว, Bridge เริ่มใหม่ และแท่งใหม่แทนที่แท่งเดิม: ไม่เกิดการรันย้อนหลังหรือการเผยแพร่คำสั่งจากชุดทดสอบนี้

ชุด `tests/test_council_total_round_deadline.py` ตรวจ deadline ที่จุดเผยแพร่คำสั่งสุดท้ายทั้ง MT4 และ MT5 รวมกรณีเวลาตรงขอบหมดอายุ ชุด Gateway เดิมตรวจ idempotency และ Guard ต่อไป

รันทดสอบแบบแยก:

```powershell
python -m unittest discover -s tests -p test_council_parallel_round_budget.py -v
python -m unittest discover -s tests -p test_council_total_round_deadline.py -v
python -m unittest discover -s tests -p test_council_worker_lease_budget.py -v
python -m unittest discover -s tests -p test_council_dispatch_reservations.py -v
```

ไฟล์ทดสอบใช้ `TemporaryDirectory` สำหรับ runtime, Workspace และ Common Files ทั้งหมด ไม่มีข้อมูลบัญชีจริงหรือคำสั่ง Broker จริงอยู่ใน fixture ผลผ่านของชุดนี้รับรองพฤติกรรมตามกรณีที่ทดสอบ ไม่ใช่หลักฐานว่าบัญชี Broker ทุกแห่งส่งออเดอร์จริงได้โดยไม่มีเงื่อนไขเพิ่มเติม
