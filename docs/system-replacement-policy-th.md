# กติกาการแทนระบบเดิมโดยไม่ทำงานซ้อน

เมื่อผู้ใช้ให้เปลี่ยนหน้าจอหรือใช้ระบบใหม่แทนของเดิม งานยังไม่เสร็จเพียงเพราะหน้าใหม่เปิดได้ ต้องย้ายความรับผิดชอบและเลิกการทำงานอัตโนมัติของระบบเดิมให้ครบด้วย

## เจ้าของงานแต่ละส่วน

| หน้าที่ | เจ้าของงานที่ต้องคงไว้ | สิ่งที่ต้องไม่กลับมาทำซ้ำ |
| --- | --- | --- |
| Sentiment และข้อมูลหน้าดาว | บริการ Sentiment Universe และ Myfxbook adapter ของบริการนี้ | FX28 trend collector และงาน Codex อธิบาย FX28 รายวันที่หน้าใหม่ไม่ได้ใช้ |
| Correlation ของหน้าดาว | MT5 reader/correlation ของ Sentiment ที่ผูกกับ MT5 ที่ผู้ใช้เลือก | การเปิด collector เก่าเพื่อคำนวณข้อมูลชุดเดียวกันโดยไม่ตรวจ dependency |
| ข่าวที่แสดงบนหน้าดาว | ข่าวและ cache ของ Sentiment ตามแหล่งข้อมูลที่ตั้งค่าไว้ | ตัวดึงข่าวเก่าที่ไม่มีผู้ใช้งานผลลัพธ์แล้ว หรือมีตารางดึงแหล่งเดียวกันซ้ำ |
| การวิเคราะห์และดูแลคำสั่งเทรด | สภา AI และ gateway ของ MT4/MT5 | ห้ามปิดตัวตั้งเวลาร่วมหรือหยุด terminal เพื่อปลดงานหน้าดาวเก่า |
| Radar/Web research | workflow และ schedule ที่ยังเปิดใช้งานจริงของ Radar | shortcut/task เก่าที่เปิดงานเดียวกันซ้ำ หรือชี้ไปยังไฟล์ที่ไม่มีแล้ว |

ตัวอย่าง compatibility ที่เก็บไว้ได้: การอ่านรายงานเก่า, schema migration, API ที่คืนข้อมูลประวัติพร้อมสถานะ retired โดยไม่ดึง provider หรือสร้าง mission ใหม่ การเก็บสิ่งเหล่านี้ไม่ใช่เหตุผลให้เปิด worker เก่าอยู่ต่อ

การย้าย Startup ของ Sentiment: ตัวติดตั้งตรวจ shortcut ชื่อ `Metafxclub Sentiment Universe.lnk` แบบอ่านอย่างเดียวก่อนเริ่ม collector หรือเพิ่ม task ใหม่ และย้ายอัตโนมัติเฉพาะ target ที่เป็น Python ของชุดติดตั้งนี้พร้อม argument เดียวเป็น `start-live.py` ของชุดเดียวกัน หลัง health ผ่านจึงลงทะเบียน task และตรวจ identity ซ้ำก่อนลบ shortcut หากเป็น prototype ภายนอก ต้องตรวจ absolute path จริงแล้วระบุ `LegacyLauncherPath` และ `LegacyPythonPath` คู่กันให้ helper การไม่รู้จัก target จะหยุดขั้น migration พร้อมคง shortcut ไว้ ไม่ถือว่าติดตั้งครบแล้ว และไม่ลบ task ภายนอกของผู้ใช้เอง

## ขั้นตอนก่อนลงมือเปลี่ยน

1. จดรายการ UI route, API, worker/thread, schedule, queue, cache และ Scheduled Task/Startup shortcut ที่เกี่ยวข้อง พร้อมเจ้าของใหม่และเก่า
2. ตรวจผู้ใช้งานผลลัพธ์เดิม โดยเฉพาะสภา AI และการเลือก MT5 แบบเก่า หากยังมี dependency ให้ย้ายหรือแสดงสถานะต้องตั้งค่าใหม่อย่างชัดเจน ห้ามสลับบัญชีหรือ terminal เอง
3. กำหนดผลปลายทางให้ชัด: อะไร active, อะไรอ่านประวัติอย่างเดียว, อะไร retired และข้อมูลเดิมใดต้องเก็บไว้
4. เก็บหลักฐานก่อนเปลี่ยนแบบจำกัดขอบเขต เช่น version, PID/start time, listener, task identity, latest successful run โดยไม่อ่านหรือบันทึก secret

## สิ่งที่ต้องทำให้ครบในการแทนระบบ

- หน้าใหม่ต้องเรียกบริการเจ้าของใหม่เพียงชุดเดียว ปิด polling และ action ของหน้าเก่าที่ไม่ใช้แล้ว รวมถึง cleanup timer, animation และ request เมื่อปิดหน้า
- ปิดการเริ่ม worker เก่าทั้งตอน startup และจากตัวตั้งเวลา รวมถึงป้องกัน API เก่าหรือ retry ปลุกงานเดิมกลับมา การปิดต้องอยู่ใน backend ไม่ใช่เพียง frontend flag
- ไม่รับงานเก่าใหม่เข้าสู่คิว ระบุงาน queued/deferred เดิมที่จะปลดอย่างเจาะจง เก็บประวัติและ audit ไว้ ไม่ยกเลิกงานส่วนอื่นหรือส่งคำสั่งซื้อขายแทนผู้ใช้
- ค่า default ของ fresh install และ upgrade ต้องใช้บริการใหม่ตรงกัน การมี config เดิมค้างต้องไม่เปิดระบบเดิมกลับมาโดยเงียบ ๆ
- ตรวจ autostart ทั้ง Task Scheduler และ Startup folder ใช้ชื่ออย่างเดียวตัดสินเจ้าของไม่ได้ ต้องตรวจ target, arguments, root และ Windows user ด้วย
- ลบหรือแทนเฉพาะ autostart ที่ยืนยัน identity ได้แล้วหลังตัวใหม่ผ่าน health ถ้าชี้ไปยัง prototype/โฟลเดอร์อื่นที่ยืนยันไม่ได้ ให้คงรายการเดิมและรายงานว่าการย้ายยังไม่ครบ ห้ามรายงานสำเร็จหรือเดา path เพื่อลบทิ้ง
- ตัว supervisor กับ worker ที่ดูแลกันถือเป็น lifecycle เดียว ต้องมี mutex/idempotency ป้องกัน collector ซ้ำเมื่อ logon, watchdog และการเปิดโปรแกรมเกิดพร้อมกัน
- การเลิกดึงข้อมูลต้องคง credentials, preferences, report และประวัติของผู้ใช้ไว้ ไม่คัดลอก credential ไปยังเครื่องอื่น

## หลักฐานก่อนสรุปว่าสำเร็จ

ทดสอบในพื้นที่แยกจากระบบเทรดจริงก่อน โดยครอบคลุม:

1. Fresh install และ upgrade จาก config เก่า: มีเจ้าของงาน active เพียงชุดเดียว
2. Cold start/restart/repeated Ensure: ไม่เริ่ม worker/provider ซ้ำ และไม่เปิดงาน retired
3. API เก่า, retry และ pending queue: ไม่ส่งงาน AI หรือดึงข้อมูลเพิ่มจากระบบที่เลิกแล้ว
4. Rollback/recovery: คงการตั้งค่าและประวัติ ตรวจว่าโค้ดปลายทางยังบังคับ retirement และไม่ปลุกงานเดิม โดยต้องระบุข้อจำกัดของการย้อนกลับข้ามเวอร์ชันด้านล่างด้วย
5. หลักฐานการดึงข้อมูล/ใช้ AI: ตรวจ request/run counts และเวลาอัปเดตของบริการจริง ไม่ใช้เพียงการเปิดหน้าได้เป็นเกณฑ์
6. สภา AI และออเดอร์: ตรวจขอบเขตการเปลี่ยนและสถานะบริการแบบอ่านอย่างเดียว ไม่ทดสอบด้วยการเปลี่ยนบัญชี/Inputs หรือเปิดปิดออเดอร์จริง

## ขอบเขตเวอร์ชันและการย้อนกลับ

การปลด FX28 และข่าวเดิมบังคับโดยโค้ดตั้งแต่ `0.9.26` ที่มีตัวป้องกัน retirement นี้ หรือรุ่นเดิมที่ได้รับแพตช์เดียวกันและตรวจยืนยันแล้ว การมีไฟล์ `legacy-market-retirement.json` หรือค่า schedule ที่ปิดไว้เพียงอย่างเดียวไม่สามารถหยุด backend รุ่นก่อน `0.9.26` ได้ เพราะโค้ดเก่าไม่อ่าน marker และยังเริ่ม FX28 อัตโนมัติ

หากการอัปเกรดล้มเหลวแล้วตัวติดตั้งคืนโค้ดรุ่นก่อน `0.9.26` พฤติกรรมเดิมอาจกลับมาพร้อมกับบริการ Sentiment ที่ถูกกู้คืน ต้องรายงานว่า **การปลดระบบเดิมยังไม่สำเร็จ** แม้ไฟล์ marker จะยังอยู่ ห้ามสรุปว่ามี pipeline เดียวจนกว่าจะนำตัวแก้ที่เข้ากันได้กลับมาใช้และตรวจ backend ที่กำลังรันจริงอีกครั้ง การกู้คืนต้องรักษาการทำงานของระบบเทรด สภา AI และข้อมูลผู้ใช้ ไม่ปิดการเริ่มสภา AI หรือหยุด terminal เพื่อกลบปัญหางานหน้าดาวซ้ำ

ยังไม่ถือว่าการย้อนกลับไปใช้โค้ดก่อน `0.9.26` ผ่านการทดสอบหรือรับประกันว่าจะไม่เปิดงานเดิม การทดสอบ rollback ที่เปลี่ยนเพียงไฟล์ `VERSION` แต่ยังใช้โค้ดใหม่ ไม่ใช่หลักฐานของการย้อนกลับข้ามเวอร์ชันจริง ต้องใช้ fixture ของโค้ดเก่าจริงก่อนรับรองความสามารถนี้

ข้อความสำหรับแจ้งผู้ใช้เมื่อเกิดกรณีนี้: “ตัวติดตั้งคืนระบบรุ่นเดิมเพื่อกู้การใช้งานแล้ว แต่การปลด FX28/ข่าวเดิมยังไม่เสร็จ ต้องนำตัวแก้ที่รองรับกลับมาใช้และตรวจอีกครั้งก่อนยืนยันว่าไม่มีระบบทำงานซ้ำ”

รายงานส่งมอบต้องระบุว่าปลดระบบใดแล้ว ยังมี compatibility ใดไว้ และมี dependency/migration ใดยังไม่ผ่าน ห้ามใช้คำว่า “แทนเรียบร้อยแล้ว” เมื่อเพียงซ่อนหน้าเก่าแต่ scheduler, API, worker หรือ autostart เดิมยังทำงานอยู่
